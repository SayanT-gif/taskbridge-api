# GitHub Copilot Custom Instructions for TaskBridge API

## Project Context
TaskBridge is a B2B SaaS microservices platform for distributed engineering teams. This repository implements the Notification & Audit Service alongside the Project Service.

## Architecture Principles
- **Microservices**: Loosely coupled, independently deployable services
- **Event-Driven**: Services communicate via well-defined events and audit trails
- **Immutable Audit Logs**: All state changes are recorded for compliance
- **API-First**: RESTful APIs with clear contracts

## Code Standards
- **Language**: TypeScript with strict mode enabled
- **Framework**: Express.js for HTTP services
- **Database**: PostgreSQL for persistence
- **Testing**: Jest with >80% coverage target
- **Linting**: ESLint + Prettier, enforce via pre-commit hooks

## File Organization
```
src/
  ├── projects/          # Project Service (existing)
  ├── notifications/     # Notification Service (new)
  ├── audit/            # Audit Service (new)
  ├── common/           # Shared utilities, types, middleware
  └── tests/            # Integration and e2e tests
```

## Naming Conventions
- **Directories**: kebab-case (e.g., `notification-service`)
- **Files**: camelCase for implementation (e.g., `projectController.ts`), kebab-case for tests (e.g., `project.spec.ts`)
- **Functions/Classes**: PascalCase for classes, camelCase for functions
- **Database Tables**: snake_case (e.g., `audit_logs`, `notification_events`)

## Service Boundaries
1. **Project Service**: CRUD operations on projects and milestones
2. **Notification Service**: Real-time notifications to team members
3. **Audit Service**: Immutable audit log queries and storage

## Key Guidelines
- Do not hardcode environment-specific values; use `.env` configuration
- All HTTP endpoints must return consistent error responses
- Database operations must be transactional where data integrity is critical
- Event emissions must include full context (actor, timestamp, change details)
- Maintain backward compatibility in API responses
- Document architectural decisions in ADRs (Architecture Decision Records)

## Testing Strategy
- Unit tests for business logic (isolated)
- Integration tests for service boundaries
- E2E tests for critical user workflows
- Fixtures for consistent test data
- Mock external dependencies

## Review Criteria
- Code follows TypeScript strict mode
- Tests pass with >80% coverage
- No security vulnerabilities (secrets, SQL injection, auth bypasses)
- Documentation updated for API changes
- Architectural diagrams included for new services
