## Issues Identified

### 🔴 CRITICAL - Security & Data Integrity

#### 1. SQL Injection Vulnerability (Medium)
**Location**: `ProjectService.ts` - `updateProjectStatus()` method  
**Issue**: While parameterized queries are used correctly, status validation relies on string matching without type safety.

```typescript
// Current approach - prone to type confusion
const validStatuses = ['active', 'archived', 'closed'];
if (!validStatuses.includes(newStatus)) { // newStatus could bypass this
  throw new Error('Invalid status');
}
```

**Risk**: Malformed status values could corrupt database state.  
**Fix**: Use TypeScript discriminated union and enum validation.

#### 2. No Authorization Checks
**Location**: All methods in `ProjectService.ts`  
**Issue**: Service methods lack authorization logic. Any authenticated user can modify any project.

```typescript
async deleteProject(projectId: string): Promise<boolean> {
  // No check: who is deleting? do they own this project?
  return this.projectModel.delete(projectId);
}
```

**Risk**: Unauthorized access to modify/delete projects.  
**Impact**: Compliance violation (GDPR, SOC 2).  
**Fix**: Inject actor context; validate ownership/team membership.

#### 3. Missing Audit Trail
**Location**: `ProjectModel.ts` - all mutating methods  
**Issue**: No logging of who changed what or when. Data modifications are not traceable.

**Risk**: Compliance violation, forensics impossible.  
**Fix**: Emit audit events on all mutations.

---

### 🟠 HIGH - Architectural & Design

#### 4. No Error Handling Strategy
**Location**: `ProjectModel.ts`  
**Issue**: Generic error messages; database errors bubble up unhandled.

```typescript
async create(data: any): Promise<Project> {
  const result = await this.db.query(query, [...]);
  return result.rows[0]; // What if rows is empty? What if query fails?
}
```

**Risk**: Inconsistent error responses to clients; information leakage.  
**Fix**: Implement error hierarchy and transformation layer.

#### 5. Loose Type Safety
**Location**: `ProjectService.ts`  
**Issue**: Constructor accepts `db: any`; method parameters are `data: any`.

```typescript
constructor(db: any) { } // Defeats TypeScript benefits
async createProject(data: any): Promise<Project> { } // No schema validation
```

**Risk**: Runtime errors; refactoring breaks silently.  
**Fix**: Define concrete types; use Zod or similar for validation.

#### 6. No Transaction Support
**Location**: `ProjectModel.ts`  
**Issue**: Multi-step operations (e.g., project + milestones) lack atomic guarantees.

**Risk**: Partial failures leave database in inconsistent state.  
**Fix**: Implement transaction management in service layer.

---

### 🟡 MEDIUM - Best Practices

#### 7. Inadequate Input Validation
**Location**: `ProjectService.ts`  
**Issue**: Only null checks; no length, format, or business logic validation.

```typescript
if (!data.name || !data.teamId) {
  throw new Error('Name and teamId are required');
}
// Missing: max length, alphanumeric check, teamId format, etc.
```

**Risk**: Invalid data enters database; downstream systems fail.  
**Fix**: Use schema validation library (Zod, Yup).

#### 8. Missing Pagination for Queries
**Location**: `ProjectModel.ts` - `getByTeam()`, `getAllProjects()`  
**Issue**: Returns all rows; no limit/offset.

```typescript
async getByTeam(teamId: string): Promise<Project[]> {
  const query = 'SELECT * FROM projects WHERE teamId = $1';
  // No pagination; could return 10,000+ rows
}
```

**Risk**: OOM errors, poor API performance, compliance risk (data exposure).  
**Fix**: Add `limit` and `offset` parameters.

#### 9. No Connection Pool Management
**Location**: Constructor assumes `db` connection exists  
**Issue**: No observable lifecycle; potential connection leaks.

**Risk**: Database connection exhaustion under load.  
**Fix**: Inject initialized pool; document lifecycle.

#### 10. Missing Logging
**Location**: All methods  
**Issue**: No structured logging for debugging or monitoring.

**Risk**: Unable to troubleshoot issues in production.  
**Fix**: Inject logger; log method entry/exit, errors, performance metrics.

---

### 🔵 LOW - Code Quality

#### 11. No Timestamps Management
**Location**: `Project.ts` interface  
**Issue**: `updatedAt` set by database; no validation in model.

```typescript
export interface Project {
  createdAt: Date;
  updatedAt: Date;
}
// But: How is createdAt set? Who ensures it's immutable?
```

**Risk**: Inconsistent timestamp handling.  
**Fix**: Clarify ownership (database vs. application).

#### 12. No Soft Delete Support
**Location**: `ProjectModel.ts` - `delete()` method  
**Issue**: Hard deletes data permanently; violates audit requirements.

**Risk**: Data loss; audit trail gaps.  
**Fix**: Implement soft deletes with timestamp.

#### 13. Incomplete Milestone Support
**Location**: `Project.ts` defines `Milestone` but `ProjectService` has no milestone methods  
**Issue**: Interface/implementation mismatch.

**Risk**: Feature incomplete; unclear ownership.  
**Fix**: Define milestone service or clarify scope.

### Issue B: Missing Audit Context

**Current**:
```typescript
async updateProjectStatus(projectId: string, newStatus: string): Promise<Project> {
  return this.projectModel.updateStatus(projectId, newStatus);
  // Who changed it? When? Why?
}
```

**Recommended**:
```typescript
async updateProjectStatus(
  projectId: string,
  newStatus: ProjectStatus,
  actor: Actor,
  auditService: AuditService
): Promise<Project> {
  const oldProject = await this.projectModel.getById(projectId);
  const updated = await this.projectModel.updateStatus(projectId, newStatus);
  
  await auditService.log({
    action: 'STATUS_CHANGE',
    resourceType: 'Project',
    resourceId: projectId,
    actor,
    changes: { status: { from: oldProject.status, to: newStatus } },
    timestamp: new Date(),
  });
  
  return updated;
}
```
